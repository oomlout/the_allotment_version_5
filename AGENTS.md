# The Allotment project instructions

For browser-platform configuration, testing or repair, read `allotment/guides/AI_PLATFORM_GUIDE.md` first. Put platform workflows in `allotment/plugins/*.yaml`; preserve the generic interpreter where possible. Never bypass the successful-test/explicit-approval gate or approve a test for the user. All browser tests and queue actions prepare drafts only. Never click Post/Send/Publish or press Enter in a composer, even for Bluesky. Final submission belongs to the user. Live preparation requires a user-authorized destination and content. Use local fixtures until those details are available.

Keep drafts, test payloads/evidence, account configuration and browser sessions under ignored `.local/`. User data repositories under `garden/` are independent and must not be staged into the tools repository. Do not change imported historical posts while developing platform support. Tests are under `tests/`; run the checks appropriate to the change and report live-platform verification limits honestly.

Keep the interface concise and functional: bold headings, direct action labels, no marketing copy, slogans, quaint language or decorative subtitles. Put detailed setup help in collapsed sections. Standard platform tests use only the fixed text in `allotment/test_sample.py` and the bundled `allotment/static/test-image.png`; do not add text editors/upload controls or override parameters for tests, and do not change the fixed sample when repairing a platform recipe.

Keep the initial countdown in the test worker, with pause/resume and Stop. Runtime after that countdown is deterministic and unattended: normal Chrome input, local screenshots/OCR and keyboard clipboard capture through the oomlout roboclick runner. Do not use browser debugging, Playwright, AI services or a mid-run assistant handoff for publishing. Preserve F8, focus/input guards, fresh coordinate checks, manual-only submission and the named desktop mutex. Implement Bluesky first; leave other platforms blocked until migrated. Walk through changes on the disposable local desktop fixture before handing them back; report live preparation and actual delivery separately.

Twitter/X, Discord server channels, WhatsApp groups and Telegram groups currently have preparation-only groundwork. Their runner must not send, publish, approve, or run a full send test. Final submission is always manual. Keep Inspect only and Prepare only separate from the publishing engine. Use `tests/desktop_preparation_practice.py` for local native checks: Send buttons and Enter are traps, and the expected attempt count is zero. `desktop_practice.py` now tests Bluesky preparation against Post/Enter traps and verifies two separate draft tabs with zero attempts. Read `allotment/guides/PREPARATION_ONLY_GUIDE.md` for these four platforms. Preserve historical Bluesky delivery evidence without treating it as approval for the new preparation engine. A checked unsent Bluesky test requires explicit user approval to enable drafting only. Chrome must use Win+Left then Win+Up and open a fresh tab for every run, leaving prior drafts untouched.
